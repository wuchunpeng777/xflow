# xflow Review

## 目标

把大规模实现压缩成有证据的业务验收报告。先与用户重建验收标准，再检查指定代码及必要依赖、运行安全验证，说明哪些要求已满足、存在偏差或尚未被证明。

不要求存在 xflow 任务 Spec。不要修改被审查代码、更新快照、格式化文件或直接开始修复，除非用户另行提出修改请求。

优先在新的 Agent 会话中运行审查。如果当前会话也生成了被审查实现，先说明本次审查并非独立上下文；除非仓库证据支持，否则不要沿用实现阶段的解释，并且只根据已确认需求和已观察证据重建结论。

## 命令

以下写法等价：

- `/xflow-review <file-or-directory>...`
- `/xflow:review <file-or-directory>...`
- `xflow review <file-or-directory>...`

## 证据规则

在整个审查过程中严格区分：

- **已确认需求**：用户明确确认或权威文档明确规定的业务意图。
- **已观察证据**：由代码、测试、命令输出、Schema 或配置支持的行为。
- **推断**：合理但没有被确认为需求或验证为事实的解释。

不得因为当前实现采用了某种行为，就把该行为反推成业务需求。不得把测试通过等同于业务正确。证据不足时，把对应验收标准标为 `未证明`。

## 流程

### 1. 确定范围

1. 解析用户指定的所有文件和目录。如果路径不存在或存在歧义，先请用户提供有效路径。
2. 把这些路径作为主要审查范围。只有在判断行为或影响所必需时，才读取范围外的调用方、依赖、测试、Schema、配置和 Git 历史。
3. 说明最终审查范围以及可用的 Git diff 或基线。Git diff 只是辅助上下文，不是使用前提。
4. 如果用户没有指定路径，先请用户提供需要审查的文件或目录。

### 2. 重建业务意图

在根据实现得出结论前完成此阶段。

1. 只读取足以提出有效问题的项目上下文，包括项目文档、manifest、现有领域术语以及指定路径的职责。
2. 每轮只提出少量高价值问题，并按实际相关性覆盖：
   - 参与者和期望结果；
   - 核心成功场景；
   - 可观察的验收条件；
   - 业务不变量和数据正确性；
   - 角色与权限；
   - 失败、重试、取消和边界情况；
   - 明确的非目标和兼容性约束。
3. 把回答整理成带编号的验收标准，优先使用 Given/When/Then 或其他可观察形式。
4. 向用户展示验收标准和假设，等待确认后再开始完整审查。
5. 如果用户拒绝澄清，只在用户明确要求时继续，并降低结论置信度，明确标记所有未解决的业务意图。

### 3. 建立实现模型

1. 定位入口、模块边界、依赖、持久化、状态变化、外部集成和失败路径。
2. 沿实现逐条追踪已确认的验收标准。
3. 检查这些路径对应的测试和验证覆盖。
4. 优先检查业务偏差，然后评估数据一致性、错误处理、权限、安全、性能、可维护性和可测试性。
5. 对问题和图中的重要节点提供具体文件及行号引用。

### 4. 安全验证

1. 从 manifest、文档和 CI 配置中发现项目已有命令。
2. 运行范围最小且相关的测试、类型检查、lint 和构建，命令不得以重写受 Git 跟踪文件为目的。
3. 不要自动更新快照或批准生成结果。
4. 不要运行可能写入生产数据、调用线上服务、发送消息、部署、迁移或产生其他外部副作用的命令，把它们列为人工验证项。
5. 记录实际执行的命令、结果以及无法完成的验证。

### 5. 绘制聚焦图

使用 Mermaid，整份报告保留一至三张图。图不能提升理解时直接省略。

1. 始终考虑绘制一张**实际架构图**，展示审查范围内的入口、核心模块、存储和外部系统。
2. 针对主要业务场景，根据已确认标准绘制**期望流程**，根据代码证据绘制**实际流程**。只有在差异仍然清晰时才合并两图。
3. 仅在数据生命周期或状态机不简单时增加数据流图或状态图。
4. 当 Git 证据足够时，把节点或连线标记为 `现有`、`新增` 或 `修改`。
5. 把没有验证的关系标为 `推断` 或 `未证明`，并且不要只依靠颜色表示高风险节点。
6. 在图旁或图例中提供文件引用。不要生成完整类图或全量文件依赖图。

### 6. 输出报告

业务符合性优先，使用以下结构：

```markdown
# Review: <scope>

## 总体结论

- 结论：符合 / 部分符合 / 不符合 / 无法证明
- 置信度：高 / 中 / 低
- 主要依据：

## 业务验收矩阵

| ID | 已确认验收标准 | 状态 | 实现证据 | 验证证据 | 业务风险 |
| --- | --- | --- | --- | --- | --- |

## 架构与流程

聚焦的 Mermaid 图、简短图例和源码引用。

## 问题清单

按照阻断、高、中、低排序。每个问题包含关联验收标准、业务影响、带文件行号的证据和建议方向，不直接修改代码。

## 工程质量

按需总结边界与耦合、数据一致性、错误处理、权限与安全、性能、可维护性和可测试性。

## 验证结果

列出实际命令、结果和仍需人工完成的验证。

## 人工下钻

只列最值得人工查看的 3 至 7 个代码位置，并说明每处的重要性。

## 未知项

列出尚未明确的需求、缺失的运行证据和外部系统假设。
```

验收状态使用 `通过`、`失败`、`部分通过` 和 `未证明`。问题等级使用 `阻断`、`高`、`中` 和 `低`。

默认只在对话中展示报告。只有用户明确要求文件和路径时，才写入 Markdown。审查报告只提供建议，不阻止其他 xflow 命令。

## 原则

- 业务意图是验收基线。
- 代码、测试和命令输出是实现证据。
- 未知不等于正确。
- 图用于压缩推理，不能代替证据。
- 把人的注意力引导到少量关键位置，不要逐文件复述实现。
